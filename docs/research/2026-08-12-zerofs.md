## What it is

ZeroFS is a log-structured filesystem that stores its durable state in an S3-compatible object store. One userspace process exposes the same filesystem through NFS, 9P, and NBD; it also has a web UI. It targets POSIX file access as well as raw block devices, without requiring a separate metadata database. [Project README](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L16-L37)

The practical use case is a persistent/shared volume backed by an S3-compatible bucket—for example, the repository’s GitHub Action accepts an object-store URL, mount path, cache settings, and encryption password. [Action definition](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/action.yml#L1-L44)

## Architecture and data path

- Protocol servers are wired to one `ZeroFS` instance: NFS, 9P (TCP or Unix socket), and NBD startup functions all receive the shared filesystem handle. [Server wiring](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/cli/server.rs#L91-L158) [NBD wiring](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/cli/server.rs#L190-L235)
- File data is broken into 32 KiB extents. The README describes compression then encryption of every extent into frames, which are packed into immutable segments (up to 256 MiB); metadata and 32-byte extent pointers live in an LSM tree on the same object store. [Extent constant](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/fs/mod.rs#L72-L75) [Architecture description](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L140-L190)
- The segment layer makes this concrete: it writes `segments/<shard>/<epoch>/<counter>` objects durably, switches large writes to multipart upload, and reads regions with object-store range requests. [Segment store](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/segment_store.rs#L1-L18) [Write/read implementation](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/segment_store.rs#L99-L136) [Range reads](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/segment_store.rs#L227-L301)
- Encryption uses XChaCha20-Poly1305 for extents. A random data-encryption key is password-wrapped using an Argon2id-derived key, stored in the object store, and conditionally initialized to avoid competing creators. [README security summary](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L28-L35) [Key lifecycle implementation](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/key_management.rs#L37-L118) [Conditional initialization](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/key_management.rs#L209-L286)

## Core workflow

1. Generate and edit a TOML configuration, providing required cache, storage, and server sections; the storage URL can target S3, Azure Blob, GCS, an S3-compatible store, or local disk. Environment references are expanded at runtime. [Configuration example and backends](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L209-L244)
2. Run `zerofs run -c zerofs.toml`, which dispatches to the server runtime; clients then mount via the native 9P kernel module, the FUSE fallback, stock Linux v9fs, NFS, or attach an NBD device. [CLI dispatch](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/main.rs#L73-L128) [Mount choices](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L251-L312)
3. For HA, configure a leader and one standby against the same bucket. The code rejects more than one peer, so this is strictly a two-participant design; automatic swaps require both a peer and a replication listener. [HA design](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L192-L204) [HA validation](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/zerofs/src/config.rs#L273-L303)

## Important trade-offs and limits

- The object store must support conditional put-if-not-exists for fencing. AWS S3 does; unsupported backends need a Redis `conditional_put` endpoint. Archive tiers are unsuitable, and infrequent-access tiers may cost more because reads are continuous. [Storage constraints](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L245-L249)
- Durability differs materially by protocol. 9P `fsync` waits for stable storage; NFS can acknowledge buffered writes and tested clients do not issue COMMIT on `fsync`. Use a 9P-based mount when `fsync` durability is required. NBD FLUSH/FUA has the stronger durable acknowledgement semantics. [9P/NFS caveat](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L251-L282) [NBD durability](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L301-L312)
- The native Linux client is an out-of-tree Rust VFS module, not FUSE or Linux v9fs. It requires x86-64 or little-endian arm64 Linux 6.18+, a matching kernel build environment, and an exact target-kernel build; strict consistency disables `mmap`. [Kernel client overview and prerequisites](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/kernel/README.md#L1-L83) [Current limitations](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/kernel/README.md#L254-L265)
- Filesystem-format maxima are 16 EiB per file and filesystem, `2^64` files over its lifetime, and `2^32` hard links per file. The project notes these are format, not proven operational, limits; provider limits and S3 cost arrive first. [Limits](https://github.com/Barre/ZeroFS/blob/26769980a5fd96fc99b30932f725631d733c1750/README.md#L330-L338)

## Bottom line

ZeroFS is best evaluated as a server-side filesystem layer over an object store, not a simple FUSE-to-S3 adapter. Its strongest differentiators are a shared core across NFS/9P/NBD, an immutable-segment plus object-store-LSM layout, encryption/compression before upload, and an optional two-node HA design. The decision hinges on whether its required conditional-write semantics, S3 latency/cost profile, protocol-specific durability behavior, and kernel-client constraints fit the intended workload.
